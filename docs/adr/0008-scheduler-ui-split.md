# 0008 调度界面：dwlle-web 做主路径，DolphinScheduler 原生界面做进阶运维
状态：已接受
日期：2026-10-10

## 背景
DolphinScheduler（DS）自带完整的 Web 界面。产品差异化在 UX 和 agent，界面需要自己掌控；但两人团队在 MVP 阶段无法重写 DS 的全部界面（尤其是 DAG 画布）。ADR-0003 只写了"短期暴露、长期封装"，需要明确 MVP 的边界。

## 决策
1. **按使用频率划分界面。**

   | 功能 | 提供方 |
   |---|---|
   | SQL IDE、NL2SQL | dwlle-web |
   | 查询一键发布为定时任务（后台调 DS API 创建工作流） | dwlle-web |
   | 我的任务、运行实例（只读）、重跑 | dwlle-web（读 DS API） |
   | 失败诊断（失败实例旁的"AI 诊断"入口） | dwlle-web |
   | DAG 画布编排、复杂依赖、补数据、告警、Worker 分组、资源中心 | DS 原生界面，新标签页深链接跳转 |

   验收标准：新用户走完"写 SQL → 发布 → 每天运行 → 失败看诊断"，全程不需要打开 DS 界面。
2. **调度定义只以 DS 为准。** dwlle 不保存 DAG 副本，只按 DS 的 workflow code / task code 挂自己的元数据（血缘、来源查询、agent 会话）。血缘在同步时按 DS 中最新的 SQL 重新解析。
3. **不用 iframe 嵌入 DS 界面**，统一使用新标签页加深链接（例如直接跳到某个工作流实例页）。
4. **所有 DS 调用集中在 dwlle-api 的一个 DS client 模块中**，锁定 DS 版本（`versions.json`），并为该模块编写契约测试。其他模块禁止直接调用 DS API。
5. **账号简化。** MVP 阶段每个 DS 项目使用一个服务账号 token；"谁做了什么"由 dwlle 审计记录。部署脚本为管理员创建 DS 账号，跳转时单独登录一次。单点登录待验证（见 ARCHITECTURE Q7）。
6. **StarRocks 任务类型做成 DS 插件**，使其在原生画布中同样可用，两边界面能力一致。

## 理由
- 重写 DAG 画布至少需要一个月，且不是差异化所在。
- DS 作为唯一事实来源，避免双向同步：用户在原生界面修改任务不会与 dwlle 冲突。
- iframe 嵌入会引入 Cookie、路由、样式和安全头问题，DS 并非为嵌入设计。
- DS 各版本 API 有变动，集中封装后升级只需改一处。

## 后果
- 进阶用户会在两个界面之间切换，体验有割裂，MVP 阶段接受。
- 服务账号模式下，DS 自身的审计日志只显示服务账号，需依赖 dwlle 审计。
- 之后按使用数据，把用户在 DS 中最高频的操作逐步搬进 dwlle-web；DAG 画布最后考虑，可能一直不做。
