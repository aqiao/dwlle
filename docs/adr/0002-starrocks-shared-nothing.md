# 0002 分析引擎：StarRocks 存算一体 on EC2
状态：已接受
日期：2026-10-09

## 背景
Athena 体验差，Redshift 对中小企业太贵。S3 GET/PUT 请求费相对国内云偏高。目标客户数据量为 GB ~ 数 TB。

## 决策
- 使用 StarRocks **存算一体（shared-nothing）** 模式，自建在 EC2 上。
- 数据存放在独立的 EBS gp3 卷；S3 只用于备份和冷数据。
- MVP 规格：单节点 FE+BE 同机部署；后续支持 3 节点。
- 优先 Graviton 机型，实例类型可配置。
- MVP 不引入 Trino。

## 理由
- 查询不访问 S3，请求费可以忽略，月成本固定、可预期。
- 一个组件即可覆盖存储、ETL、ad hoc 查询和报表。MySQL 协议在国内生态熟悉度高。
- 在这个数据量级下，存算分离的弹性收益小于其复杂度。
- Trino 没有自己的存储，每次查询都读 S3，与成本目标冲突；Athena 本身就基于 Trino。

## 后果
- 我们要负责引擎运维：安装、升级、备份、恢复。必须做到一键化。
- 单节点没有高可用，依赖 EC2 自动恢复 + EBS 快照 + 逻辑备份；需要在产品层面明确告知客户 RPO/RTO。
- 待验证：StarRocks ARM64 版本的生产可用性（ARCHITECTURE Q1）。
- 将来客户数据量变大时，可迁移到存算分离；届时另起 ADR。
