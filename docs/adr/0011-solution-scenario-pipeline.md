# 0011 解决方案、业务场景与 Pipeline 三层抽象

状态：已接受
日期：2026-11-03

## 背景

只复用单个 Pipeline 无法完整交付一个业务目标。真实场景通常需要多条 Pipeline 协作，并依赖数据源、权限、基础设施和运行环境。如果全部平铺给终端用户，会增加理解成本；如果直接复制完整项目，又可能泄露密钥、扩大权限或绑定原作者环境。

## 决策

1. **固定三层产品模型，不允许场景多层嵌套。**
   - Project：运行与治理边界，包含环境、基础设施绑定、权限、数据源和密钥引用。
   - Scenario：业务目标与跨 Pipeline 协作边界，包含 Pipeline 引用、依赖、数据契约、SLA 和负责人。
   - Pipeline：可独立版本化与执行的数据工作流，包含技术节点、引擎、重试和质量配置。

2. **可共享的项目级产物称为 Solution。** Solution 是版本化模板，不复制正在运行的项目实例。Solution Manifest 包含 Scenario/Pipeline 版本引用、组件需求、基础设施需求、角色需求和数据源契约。

3. **定义与环境绑定分离。** 安装 Solution 时，由目标用户绑定自己的环境、云资源、数据源、密钥和角色。不得复制原作者凭据或实际授权；权限和云资源创建必须经目标管理员确认。

4. **场景不是文件夹。** Scenario 具有整体状态、跨 Pipeline 依赖、SLA、失败影响和数据血缘。跨 Pipeline 启动条件优先表达为数据分区就绪、新鲜度和质量结果等数据契约，而不只是上游任务成功。

5. **使用版本引用，避免复制。** 场景只引用同一项目内的 PipelineVersion；Solution 锁定 Scenario/Pipeline 和组件版本。首版不允许跨项目 Pipeline 引用，发布时检查循环依赖和兼容性。

6. **渐进式 UI。** 默认向业务用户展示 Scenario，向工程师提供 Pipeline 编辑器，向管理员提供 Project/环境绑定。三层不能同时以同等复杂度堆叠在一个页面中。

7. **分阶段交付。** Alpha 在领域模型和 API 中预留 Scenario/Solution，原型展示完整路径；生产实现先完成场景分组与依赖，再实现 Solution 安装，最后开放共享市场。

## 理由

- 三层分别解决运行治理、业务协作和技术执行，比单纯增加 Pipeline 数量更适合业务复用。
- Solution 与环境绑定分离，使项目级复用不会以泄露凭据或扩大权限为代价。
- 数据契约比单纯任务成功依赖更能覆盖补数据、重试和部分成功。
- 固定层级与版本引用可控制循环依赖、权限扩散和维护成本。

## 后果（含代价与风险）

- 控制平面需要维护 Scenario/Solution 的版本、依赖和兼容性模型。
- 跨 Pipeline 状态和数据契约会增加元数据与调度复杂度。
- Solution 安装必须提供权限、成本和基础设施审查，不是简单导入 JSON。
- DS 不直接理解三层模型，由 dwlle 负责场景协调和 Pipeline 编译，不能绕过自有协议。
