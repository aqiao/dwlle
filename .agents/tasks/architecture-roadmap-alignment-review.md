# 架构文档与路线图一致性审查

## 摘要结论

本次只读审查完整阅读了 `docs/ARCHITECTURE.md` 与 `docs/ROADMAP.md`，未读取或审查 ADR、任务文档、开发计划、README、代码或部署内容。

发现 3 项会使实施者对阶段范围或任务治理产生歧义的问题：

1. **中等**：Alpha 阶段的只读 AI 基础闭环只在路线图中列为阶段目标，架构阶段能力方向未列出该能力。
2. **中等**：Preview 阶段两份文档分别列出不同的能力方向，未说明哪些是完整范围、哪些是补充项。
3. **中等**：路线图将新任务说明统一写为 `Txxx-*.md`，而架构术语与规范将 `Txxx` 定位为历史任务表示；新任务的文档编号与分支/提交编号之间没有明确的统一规则。

除上述事项外，两份文档在产品与客户界面边界、控制面/数据面、核心领域术语、服务/API/权限上下文、Alpha 至 GA 的顺序和日期、血缘与质量权威边界、以及主要部署约束上相互一致。

## 证据与发现

### 1. Alpha 阶段遗漏只读 AI 基础闭环

- **严重程度**：中等
- **位置**：
  - `docs/ARCHITECTURE.md:66-75`，§2.1「阶段与开发计划」；尤其是 Alpha 行 `:71`。
  - `docs/ROADMAP.md:8-17`，§「阶段路线」；尤其是 Alpha 行 `:11`。
  - 补充定位：`docs/ARCHITECTURE.md:290-303`，§9「AI 辅助运维」；`docs/ARCHITECTURE.md:353-361`，§12 的 Q5 标为 Alpha。
- **相互冲突证据**：
  - 架构文档明确表示该表维护「阶段时间和能力方向」，但 Alpha 仅写「自研控制平面、DolphinScheduler 工作流、Trino 查询与基础质量检查」。
  - 路线图的 Alpha 目标在相同时间段额外写有「只读 AI 基础闭环」。
  - 架构文档自身的 AI 基础能力是失败诊断，并将模型日志脱敏与诊断证据质量（Q5）归属 Alpha。因此这不是仅由路线图引入的全新远期设想。
- **实际影响**：仅依赖架构阶段表拆分 Alpha 工作的实施者，可能将 AI 诊断及其脱敏验证误判为未纳入 Alpha 的后续能力；仅依赖路线图的实施者则会将其纳入 Alpha。两份文档对「能力方向」的边界不一致。
- **最小文档修复建议**：在架构文档 §2.1 的 Alpha 能力方向追加「只读 AI 失败诊断基础闭环」，或在该行明确路线图所列 AI 闭环属于该阶段表的已知补充范围。

### 2. Preview 阶段能力方向不一致

- **严重程度**：中等
- **位置**：
  - `docs/ARCHITECTURE.md:66-75`，§2.1 的 Preview 行 `:73`。
  - `docs/ROADMAP.md:8-17`，§「阶段路线」的 Preview 行 `:14`。
- **相互冲突证据**：
  - 架构文档将 Preview 描述为「邀请制试运行、反馈处理、发布准备、网站与社区建设」。
  - 路线图将同一阶段描述为「邀请制试运行、反馈处理、升级恢复和 GA 准备」。
  - 两处共用同一阶段名称和日期，但一方未提「升级恢复」，另一方未提「网站与社区建设」，也没有定义二者为可选项、补充项或由不同阶段计划承担。
- **实际影响**：实施者无法仅凭这两份顶层文档确定 Preview 的阶段范围是否同时包含升级/恢复与网站/社区建设，进而可能在阶段计划、任务归属和验收中漏项或产生重复解释。
- **最小文档修复建议**：统一两张阶段表的 Preview 能力方向。若四项均属 Preview，使用同一合并表述；若其中一项不属于平台交付范围或只是支持性工作，应在两份文档中以相同方式标注其边界。

### 3. 新任务说明的编号规范与 `Txxx` 的历史定位不一致

- **严重程度**：中等
- **位置**：
  - `docs/ROADMAP.md:41-47`，§「每个任务的流程」第 1、3 步。
  - `docs/ARCHITECTURE.md:376-395`，§13.3「GitHub 分支命名」；尤其是 `:392`。
  - `docs/ARCHITECTURE.md:398-414`，§13.4「提交信息规范」。
- **相互冲突证据**：
  - 路线图要求设计方为每个任务新建 `docs/tasks/Txxx-*.md`，随后按架构规范建分支，并以 `Task-xxxx:` 提交。
  - 架构规范将 `Txxx` 明确称为「历史 `Txxx` 任务」，并规定其在新建分支时补足为 `Task-xxxx`；新分支及提交都使用四位数字的 `Task-xxxx`。
  - 两份文档没有规定新建任务说明究竟应继续使用 `Txxx`，还是改用 `Task-xxxx`，也没有规定二者在任务标识、前导零和对应关系上的正式映射。
- **实际影响**：设计方可能按路线图为新任务创建 `T019-*`，而编码 agent 又按架构规则创建 `Task-0019` 分支和提交；另一些实施者可能直接新建 `Task-0019-*` 文档。该歧义会破坏「一个任务对应一个分支」的可追溯性，并使自动化、PR 和验收记录难以稳定关联。
- **最小文档修复建议**：选定一种新任务说明命名并在两份文档使用同一规则。建议将路线图第 1 步改为 `docs/tasks/Task-xxxx-*.md`；若必须保留 `Txxx` 文件名，则明确它是唯一允许的文档例外，并规定 `T019 → Task-0019` 的映射适用于新旧任务及其验收记录。

## 已确认一致的要点

以下内容在两份文档中直接一致，未发现会导致实施歧义的冲突：

- **产品和客户界面边界**：自研 SaaS 控制平面及全部客户界面；DolphinScheduler 和 OpenMetadata 原生 UI 仅供内部管理员。见架构 §1.1 第 1-2 条、§4.1（`docs/ARCHITECTURE.md:19-21, 100-137`）及路线图「跨阶段架构约束」第 1 条（`docs/ROADMAP.md:20-25`）。
- **控制面与数据面职责**：架构明确控制平面处理配置、权限、业务元数据和编排指令，数据平面处理实际读写、计算和任务运行；路线图的 DS 工作流、Trino、SeaTunnel/Polaris 和 OpenMetadata 阶段目标没有改变这一划分。见 `docs/ARCHITECTURE.md:13-15, 32-61` 与 `docs/ROADMAP.md:11-14`。
- **领域术语与数据权威**：Tenant、Workspace、Environment、Scenario、Workflow、DataAsset 和 DataAssetBinding 的定义与路线图使用方式一致；DataAsset 统一身份、OpenMetadata 为 LineageEdge 唯一权威、dwlle 为 QualityRule/QualityResult 权威、Trino 执行 SQL 质量检查均一致。见架构 §5、§6、§13.1（`docs/ARCHITECTURE.md:151-303, 344-365`）及路线图「跨阶段架构约束」（`docs/ROADMAP.md:20-25`）。
- **服务/API/权限边界**：公共 REST、FastMCP、统一 `tenant + workspace + actor + agent + scopes` 上下文和客户不能直接访问 DS/OpenMetadata 管理接口均由架构定义；路线图没有给出相反约束。见 `docs/ARCHITECTURE.md:203-251`。
- **阶段顺序和日期**：两份表均为 Alpha（2026-11）→ Beta（2026-12）→ Preview（2027-01）→ GA（2027-02），日期完全相同。见 `docs/ARCHITECTURE.md:66-75` 与 `docs/ROADMAP.md:8-17`。
- **任务治理的其余部分**：路线图要求任务属于一个阶段、声明范围和验收、完成测试与两分区 synth 后评审；架构的分支类型、四位 `Task-xxxx`、英文动词开头提交及小而完整提交规则与之兼容。见 `docs/ARCHITECTURE.md:376-414` 与 `docs/ROADMAP.md:41-47`。
- **明确开发约束**：路线图的「不从公网下载、第三方组件进入版本与制品清单」与架构的同一约束一致。见 `docs/ARCHITECTURE.md:314-320` 与 `docs/ROADMAP.md:20-25`。

## 结论与建议

应优先统一两张阶段表中的 Alpha 和 Preview 能力方向，并在路线图与架构术语规范之间确定新任务说明的唯一编号格式。这三项都只需文档文字调整，不需要变更架构、ADR、任务、代码或部署。

无法仅凭这两份文档判断的事项包括：各阶段开发计划是否已经承接上述遗漏、现有任务文件及分支的实际命名存量、以及 ADR 是否对任一能力有更具体的取代关系。本审查按限定范围未读取这些材料，因此不对其作结论。
