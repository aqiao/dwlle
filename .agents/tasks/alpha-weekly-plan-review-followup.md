# Alpha 周计划第二轮只读审查报告

## 摘要结论

本轮仅完整审查了 `docs/PROJECT_PLAN_ALPHA.md`，并仅以 `docs/ARCHITECTURE.md` 与 `docs/ROADMAP.md` 作范围边界核对。发现两项会影响任务执行、进度判断或 A5 联调排程的文档歧义，均建议在 Alpha 计划中作最小补充后再进入执行。

上一轮关注项的处理结果如下：

- **Scenario/Solution P0 最小模型与只读原型：已实质处理。** 计划明确将 T021/T022 的只读原型与 T035 的真实 Scenario 模型共同作为证据，并排除 P1 的 T0077 作为唯一证据。
- **恢复、备份、重复部署、保留和未实施项交接：已实质处理。** T0066/T0067 给出产品 RDS、DS、Keycloak、后台 Catalog、S3 CTAS 数据及实装持久卷的恢复矩阵；OpenMetadata 与 Polaris 产品化也明确为 Alpha 不适用并交接 Beta。
- **冻结期与周排程：一致。** 11-25 前完成功能编码，11-26 至 29 限于缺陷、证据与文档；相应的 T0067/T0068 均属允许范围。
- **A5、T0069、T0070 双分区 synth 和 `arn:aws:` 模板检查：已明确要求证据。** T0069 要求记录候选 SHA、Global/CN synth 和 ARN 检查输出，T0070 要求形成可追溯验收记录，第 7 节第 14 项进一步要求记录命令、SHA、时间和输出。
- **阻断缺陷一缺陷一任务一分支一验收记录：已明确。** 计划禁止通用修复分支，要求每个缺陷具有唯一任务说明、分支和回归证据，并由 T0070 引用。

无法仅由这三份文档文本确认的事项：历史任务文件中的交付记录是否真的包含所述测试和验收证据；各计划日期下的人力是否足够；实际 AWS 部署、恢复、重复部署、两分区 synth 与模板检查是否已经或将会通过。这些都需要任务记录或实际执行输出，故本次未作事实判断。

## 证据与发现

### F1（P1）：第 5.1 节列出的历史 Alpha 任务未具备计划声明的逐任务责任、交叉审核与计划日期字段

**文件与行号**：`docs/PROJECT_PLAN_ALPHA.md:109-132`、`:102-105`

**文本证据**：

- 第 5 节声明：“一个 Git 任务对应一份 `docs/tasks/Txxxx-*.md` 和一个任务分支”。
- 同节规定状态集合为“未开始、进行中、阻塞、已实现待验收、已验收、不适用”，并要求“每项至少由另一角色交叉审核”。
- 第 5.1 节的历史任务表只有“任务、状态、可追溯交付与验收证据”三列。例如 T019 至 T041 和 T0001 都没有 Owner、审核人或目标日；且多数状态写作“已完成（历史）”，不在该节定义的统一状态集合内。

**实际影响**：

执行者或进度跟踪者无法从计划本身判断这些历史基线由谁负责复核、由谁交叉验收、应在何时完成 A5 前的证据复核。“已完成（历史）”虽被解释为已有交付记录，但不能与本计划的“已验收”状态直接比较，因而无法机械执行第 5.7 节“前置任务必须达到已验收”的合入门禁。该问题尤其影响以 T021/T022/T035 作为 P0 Scenario/Solution 证据时的责任归属和验收状态判定。

**最小文档修复建议**：

为第 5.1 节增加一个不改变历史任务的“历史基线复核”表，至少列出所有被 Alpha P0 或后续任务直接依赖的历史任务（包括 T021、T022、T035、T036-T041、T0001），以及 `Owner / 审核`、`A5 前复核目标日`、计划统一状态和证据链接。或者在现有表增加上述列，并把“已完成（历史）”映射为明确的计划状态，例如“已实现待验收”，直至指定验收角色复核后更新为“已验收”。

**建议验证方法**：

在计划文本中逐项核对所有第 5.7 节所称“直接依赖历史基线”的任务，确认每项均可从第 5.1 节找到 Owner、另一角色审核人、A5 前复核日期、统一状态和证据引用；再确认作为 P0 Scenario/Solution 证据的 T021、T022、T035 均包含这些字段。

### F2（P1）：T0069 的明确前置集合不足以表达 A5 必须等待的关键 P0 集成与证据任务

**文件与行号**：`docs/PROJECT_PLAN_ALPHA.md:200-201`、`:220-230`、`:264-279`

**文本证据**：

- T0069 的任务级验收是“第 7 节全部适用项通过；记录候选 SHA、Global/CN synth 和 ARN 检查输出”。
- 第 7 节的端到端验收包含 Workflow UI 主链路、SQL/质量与告警、AI 诊断、恢复/重复部署、成本/日志/保留和模板检查。
- 但第 5.7 节只把 T0064、T0065、T0066 列为 T0069 的前置任务；T0059（主链路 UI 联调）、T0063（AI 诊断降级与反馈）、T0067（部署/恢复手册）和 T0068（演示、限制与 Beta 交接）均没有在该节明确为 T0069 的前置或验收输入。
- 第 5.7 节同时规定前置任务须先达到“已验收”，而 T0070 要求以 T0069 的全部适用证据为前置。

**实际影响**：

第 5.7 节被标题定义为“跨任务依赖与合入门禁”，但按其显式关系，A5 可以在仅 T0064-T0066 已验收时排程或创建联调分支；这与 T0069 实际必须执行的 UI、AI、运维手册和交接验收输入不一致。执行者需要自行推断哪些未列出的 P0 工作必须先合入并验收，导致候选 SHA、A5 起始条件和阻断责任的判断不一致。

**最小文档修复建议**：

在第 5.7 节将 T0069 的前置条件补充为：所有支持第 7 节适用操作的实施任务已验收，至少显式列出 T0059、T0063、T0064、T0065、T0066、T0067、T0068，并说明 T0069 在这些已合入候选基线上执行。若 T0067/T0068 允许在 A5 同日完成，应改为明确的“提交给 T0070 的必备输入”，而非留给执行者推断。

**建议验证方法**：

修订后，从第 7 节第 1 至 14 项反向追踪到第 5.2 至 5.4 节的交付任务，确认每个适用验收操作都有已验收的前置任务或明确的历史证据；再确认 T0069 的候选 SHA 只能在这些前置任务合入后产生，T0070 仅引用该候选上的实际输出。

## 一致项与结论

`docs/PROJECT_PLAN_ALPHA.md` 对 Alpha 的边界与 `docs/ARCHITECTURE.md:70-76`、`docs/ROADMAP.md:10-13` 一致：Alpha 是自研控制平面、DolphinScheduler、Trino、基础质量检查和只读 AI 失败诊断；后台 Iceberg Catalog 可为 CTAS 部署，Polaris 产品化、SeaTunnel 全流程及 OpenMetadata 血缘端到端集成仍在 Beta。计划也没有把生产 Scenario 调度、Solution 实际安装、FileAsset 实装、OpenMetadata 或 SeaTunnel 流程隐式重新纳入 Alpha P0。

建议仅修复 F1 与 F2 后继续执行。除这两项外，本次未发现可由指定三份文档文本直接证实、且会造成执行、进度判断或阶段验收歧义的矛盾或遗漏。
