# Alpha 周计划只读审查报告

## 摘要结论

审查范围仅限 `docs/PROJECT_PLAN_ALPHA.md`，并以 `docs/ARCHITECTURE.md` 和 `docs/ROADMAP.md` 为边界核对；未阅读 ADR、任务说明、README、Backlog、代码、部署文件或既往审查报告，也未将计划中的分支字段与实际 Git 状态对照。

计划的阶段目标、日期、P0 主链路和明确延后项总体与架构及路线图一致：Alpha 聚焦自研控制平面、DolphinScheduler、Trino、基础质量检查和只读 AI 诊断；SeaTunnel 全流程、Polaris 产品化及 OpenMetadata 血缘没有被错误纳入 P0。T0043～T0078 的建议分支名也均满足新任务的 `类型/Txxxx-小写短横线描述` 格式。历史 `task/T019-*`～`task/T042-*` 按文档明确的历史例外处理，不构成命名问题。

但当前周计划尚不能可靠地作为 Alpha 进度与验收依据。发现 7 项问题，其中 2 项高、4 项中、1 项低：P0 的 Scenario/Solution 最小范围没有明确归属任务；恢复验收没有覆盖已部署且架构声明的恢复对象；各任务没有各自的可观察验收标准和责任人；关键依赖与最终双分区 synth 证据没有被显式编排；以及 T0071 的条件缺陷分支定义不能保持“一任务一分支”。以下建议均为最小文档修复，不建议在本审查中修改任何代码或实现范围。

## 证据与发现

### 高：P0 的 Scenario/Solution 最小模型与只读原型未分配到 P0 任务

- **位置与证据**：`docs/PROJECT_PLAN_ALPHA.md:54` 将“Scenario/Solution 领域模型与只读原型”列为 P0。现有任务中，T0044（第 125 行）仅包含 Tenant、Workspace、Environment；T0050～T0060（第 139～147 行）没有 Scenario 或 Solution；唯一涉及 Scenario 的 T0077（第 188 行）位于 P1，且范围还包含跨 Workflow 依赖与数据契约。计划第 109 行只笼统称已完成“初版领域模型”，没有将该 P0 完成定义映射到具体历史任务或验收证据。
- **架构边界**：`docs/ARCHITECTURE.md:20-23` 把 Scenario 作为三层领域模型的一层，并规定 Solution 保存可移植定义；`docs/ARCHITECTURE.md:165、181-182` 分别定义 Solution 与 Scenario 的领域职责。路线图 `docs/ROADMAP.md:47` 要求跨阶段依赖和未验收项在阶段计划中显式记录。
- **实际影响**：团队可能将 P1 的 T0077 视为唯一 Scenario 工作，导致 P0 声明的 Scenario/Solution 最小模型和只读原型既没有交付任务也没有验收，进而把“已完成的初版领域模型”误判为满足 P0。
- **最小文档修复建议**：在 5.1 的历史基线条目中，逐项注明哪一个既有 T019～T041 任务交付并验收了 Scenario/Solution 最小模型和只读原型，及其证据位置；若该能力尚未交付，则在 5.2 或 5.3 新增一个 P0 任务，只覆盖领域模型、只读原型、权限/审计及不影响 Workflow 主链路的验收。保留跨 Workflow 依赖、数据契约展示等 T0077 的 P1 范围。
- **建议验证方法**：为该任务说明定义并执行自动化领域/API 测试，证明可在 Workspace 内读取 Scenario/Solution 原型，且不产生生产调度或实际安装；在 T0069 的真实 AWS 验收记录中链接测试结果。检查 P1 T0077 未被用作该 P0 条目的唯一完成证据。

### 高：恢复与保留验收范围不足，未明确 DS、Keycloak 与 S3 数据保护的处理

- **位置与证据**：T0066 在 `docs/PROJECT_PLAN_ALPHA.md:160` 只写“RDS/Catalog 恢复、重复部署及保留策略验证”。第 236 行的端到端第 12 项也只恢复“产品元数据库和后台 Catalog”。第 65 行 P0 运维要求一次恢复验证与重复部署验证，而第 238 行仅以“保留策略符合配置”概括卸载检查。
- **架构边界**：`docs/ARCHITECTURE.md:314` 规定 RDS、S3 开启备份/版本保护，恢复范围明确涵盖产品数据库、DS、Keycloak、Polaris、OpenMetadata 元数据库和搜索索引重建。计划已在第 242～243 行明确 OpenMetadata 与 Polaris 产品化的部分 Alpha 不适用项，但没有同样声明 DS、Keycloak、S3/业务数据的恢复范围或不适用理由。`docs/ARCHITECTURE.md:298` 还规定数据卷、S3 数据桶和 RDS 默认保留。
- **实际影响**：即便第 12 项通过，也无法证明已部署的身份与调度配置可以恢复，或 S3/CTAS 数据在卸载与重复部署后受到保留保护。该缺口会使 P0 的“恢复验证”“保留策略”完成定义产生错误的完成结论。
- **最小文档修复建议**：将 T0066、T0067 与第 12/13 项的验收对象明确为产品 RDS、DS、Keycloak、后台 Catalog/Polaris、S3 中 CTAS 数据与相关持久卷，并分别写明备份来源、恢复动作、可观察恢复结果和重复部署后的资源唯一性。若 OpenMetadata 尚未部署，保持现有 Beta 交接；若其余对象不在 Alpha 实装范围，逐项标为“未实施，不适用”并写入 T0068 的 Beta 交接清单。
- **建议验证方法**：在目标 AWS 账号按手册恢复每个 Alpha 实装的状态性组件，在恢复后使用 OIDC 登录、读取已发布 Workflow/DS 映射并读取既有 CTAS 表；再运行部署脚本，记录无重复资源及数据保留的证据。将未实测对象列入 T0070 未验收项。

### 中：任务表没有任务级验收标准，交付物和“完成”无法客观判断

- **位置与证据**：5.2～5.6 的表仅含“编号、任务与交付物、建议分支”（`docs/PROJECT_PLAN_ALPHA.md:122-130、136-147、154-162、169-172、181-188`），没有验收列。第 131、149、164 行只列部分依赖。第 20～25 行、49～65 行虽然有阶段/P0 完成定义，第 224～238 行有最终端到端操作，但不能判定单个任务，例如 T0048 的指标/告警、T0049 的成本基线、T0061 的脱敏、T0065 的每种配额或 T0067 的手册是否已达成。
- **路线图边界**：`docs/ROADMAP.md:43` 要求每个任务说明明确阶段、范围和验收标准，`docs/ROADMAP.md:45-47` 要求任务验收、真实 AWS 验证与未验收项如实记录。仅凭本计划无法确认每项任务说明是否存在，且用户要求审查的是该周计划本身的清晰度。
- **实际影响**：分支/任务状态容易按“已编码”而不是“已验证”标为完成，最终验收失败后也无法定位缺少哪项任务交付物或测试证据。
- **最小文档修复建议**：为每个 T0043～T0070（以及已完成基线的每个可追溯任务）增加“验收标准/证据”引用，至少明确可观察结果、自动化或目标账号验证方式、适用的安全/权限/脱敏/审计条件和输出位置。P1 任务标明“不计入 P0”，条件任务 T0071 标明触发条件及其缺陷验收。无需把任务说明全文复制到计划。
- **建议验证方法**：在 A5 前以该列逐项检查证据链接或命令输出；T0070 汇总每项为“通过、未通过、未实测、不适用（含交接）”，而不是只写阶段总状态。

### 中：责任归属与状态粒度不足，且 A4 时间窗会导致功能冻结进度误判

- **位置与证据**：资源假设只给出“平台工程师 1 名、产品工程师 1 名、设计/评审/验收投入”（`docs/PROJECT_PLAN_ALPHA.md:29-34`）；所有新任务表只列编号、交付物、建议分支，未列 Owner、协作/审核人、状态或目标完成日（第 122～188 行）。5.1 的“当前状态”表仅以“已完成/进行中”描述聚合历史范围和 T042（第 110～116 行），没有完成定义、验收证据或阻塞状态。A4 工作安排的窗口是 11-23～11-29（第 152 行），但里程碑规定 11-25 后只能修复缺陷和补充文档（第 99 行）。
- **实际影响**：无法按“每个人任务”追踪谁负责交付、谁负责依赖或验收，也无法判断在 11-25 后继续进行的 T0061～T0066 是合规的缺陷修复还是新增 P0 功能。历史基线的“已完成”也会被误读为已满足第 20～25 行的完成定义。
- **最小文档修复建议**：为每个任务增加 Owner、必要协作/验收人、计划完成日、状态（未开始/进行中/阻塞/已实现待验收/已验收/不适用）和验收证据引用；对 T019～T042 给出逐任务状态或明确链接到逐任务清单。将 A4 的编码任务计划完成日限定在 11-25，11-26～29 仅保留缺陷、证据收集和文档，或在计划中批准并记录新的冻结日期。

### 中：关键跨任务依赖没有显式列出，排程无法保证可构建的交付顺序

### 中：A5 端到端验收没有显式纳入双分区 synth 的可观察证据

- **位置与证据**：阶段完成定义要求两个 AWS 分区均可 `cdk synth`（`docs/PROJECT_PLAN_ALPHA.md:23`）；第 50 行也将 Global/中国区配置 synth 列为 AWS 部署完成定义；第 207～220 行给出工程质量命令与模板检查。但最终验收第 224～238 行只覆盖真实 AWS 环境、业务链路、安全、恢复、成本与卸载，没有要求运行两个 synth 命令、检查模板中不存在 `arn:aws:`，也没有把输出纳入 T0069/T0070 的证据。
- **架构与路线图边界**：`docs/ARCHITECTURE.md:95` 规定 IaC 为“两分区 synth，实测范围由阶段计划确定”；`docs/ROADMAP.md:45` 要求在代码评审前完成“两分区 synth”。
- **实际影响**：Global 真实部署成功不能证明中国区配置可 synth，也不能证明模板符合分区兼容约束；阶段可能在缺少 P0 完成定义的证据时被标为验收通过。
- **最小文档修复建议**：在 T0069 交付物和第 7 节新增一个验收项：执行第 6 节的 `dev-global`、`dev-cn` synth 与模板 ARN 字面量检查，记录命令、时间、提交 SHA 和结果到 T0070。明确这是 synth 验证而非中国区真实部署，保持既定 Alpha 边界。
- **建议验证方法**：在验收候选提交上运行第 207～215 行命令；两个 synth 成功且模板遍历检查通过，并把完整输出或可追溯 CI 链接附入 T0070。

### 低：T0071 的条件“阻断缺陷”分支不能稳定满足一任务一分支和可追溯命名

- **位置与证据**：`docs/PROJECT_PLAN_ALPHA.md:172-174` 将 T0071 定义为“仅用于验收阻断缺陷，按实际缺陷重命名”的一个条件分支；第 193～195 行规定按依赖合入且以任务为单位管理。架构的命名规范要求一个任务对应一个分支，且分支与任务说明、提交、交付记录用同一标识（`docs/ARCHITECTURE.md:377、388-392`；其中第 392 行明确“一个任务对应一个分支”）。
- **实际影响**：若发现多个不相关阻断缺陷，一个通用 T0071 不能同时对应多个缺陷任务；若“按实际缺陷重命名”而仍使用 T0071，则任务描述、任务说明与交付记录难以保持一一映射，进度表也可能把多个修复合并成一个“完成”。
- **最小文档修复建议**：将 T0071 改为“验收阻断缺陷的登记/汇总任务，不创建代码分支”；每个实际阻断缺陷新建一个 `bugfix/Txxxx-实际缺陷描述` 任务、分支和验收记录，并在 T0071/T0070 汇总。没有阻断缺陷时维持不创建分支。
- **建议验证方法**：出现阻断缺陷时，检查每个缺陷都有唯一 Txxxx 任务说明、唯一 `bugfix/` 分支名和对应的回归证据；T0070 引用这些条目而不把它们合并为一个通用分支。

- **Alpha 范围一致**：计划第 12～17 行、45～86 行的核心链路与架构/路线图的 Alpha 定义一致（`docs/ARCHITECTURE.md:71、76`；`docs/ROADMAP.md:11`）。没有将 SeaTunnel 全流程、OpenMetadata 血缘或 Polaris 产品化错误列作 Alpha P0。
- **安全与权限主题已被纳入，但需任务级证据**：T0001/T0047/T0061/T0064/T0065 与第 7 节第 2、3、7、10、11、13 项覆盖了 OIDC/RBAC、Secrets Manager、脱敏、租户越权审计、查询/配额、无敏感日志和保留策略。它们与架构的租户上下文、三角色、脱敏和只读诊断约束相符（`docs/ARCHITECTURE.md:289-298、304-307`）。本审查不能仅凭计划文字确认实现或测试充分性。
- **P1 与交接边界清楚**：第 67～77 行将 FastMCP 等列为 P1；第 240～246 行明确 MCP、OpenMetadata 与 Polaris 产品化的不适用/交接要求，符合架构的“未实施则标注不适用并明确交接”原则（`docs/ARCHITECTURE.md:322-330`）。
- **建议分支名称格式正确**：新计划任务 T0001、T0043～T0078 均使用允许的 `feature/`、`doc/` 或 `bugfix/` 前缀，T 编号为四位，描述小写短横线形式；T0071 的结构性可追溯问题见上。历史 T019～T042 以计划第 105～116 行和架构的历史例外规则处理，未做实际 Git 状态对照。

## 无法仅从文本确认的事项

- T019～T042、T0001、T0042 所谓“已完成/进行中”是否存在对应任务说明、PR、测试、部署或验收证据。
- T0043～T0078 是否已各自建立任务说明，以及任务说明是否补充了本文指出的任务级验收、责任人和依赖。
- 两分区 synth、模板 ARN 检查、真实 AWS 部署、恢复演练、越权审计、日志脱敏和性能/配额测试是否实际通过。
- 实际 Git 分支是否存在、是否符合命名或是否与计划字段一致。该项按审查指令未检查。

## 结论与建议优先级

在将计划用作 Alpha 进度面板或开始 A2 以后工作前，建议先完成以下纯文档调整：

1. 补齐 P0 Scenario/Solution 最小模型的明确任务归属和验收，或链接其历史任务证据。
2. 重新界定 T0066/T0067 与第 7 节的恢复、备份和保留范围，逐项覆盖 Alpha 实装组件或明确不适用及交接。
3. 给所有任务增加 Owner、日期、状态定义、显式依赖和可观察验收/证据引用，并把双分区 synth 纳入 A5 证据。
4. 将 T0071 改为验收缺陷汇总记录，实际缺陷使用独立 Txxxx `bugfix/` 任务与分支。

以上修复不改变 Alpha 功能范围，只使现有 P0/P1 边界、进度状态和验收证据可追溯、可观察。
